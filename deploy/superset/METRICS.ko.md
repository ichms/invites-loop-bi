# 지표 가이드 — 메트릭 추가하는 법

지표(metric)는 **대시보드가 아니라 SQL 뷰에 정의**되어 있습니다.
이 문서는 그 이유와, 새 지표를 추가하는 절차를 설명합니다.

작성 기준일: 2026-08-11

---

## 1. 왜 대시보드에 SQL 을 넣지 않는가

지표를 대시보드 카드 안의 SQL 로 만들면, 6개월 뒤에는 "활성 사용자" 가
서로 조금씩 다른 정의로 네 군데에 존재하게 됩니다. 그리고 어느 것이 맞는지
아는 사람이 아무도 없습니다. 회의에서 두 사람이 다른 숫자를 들고 오면,
그 다음부터는 대시보드 전체를 아무도 믿지 않습니다.

그래서 이렇게 합니다:

- 지표 = `marts` 스키마의 **뷰 하나**. 이름 앞에 등급이 붙습니다.
- 정의를 바꾸려면 **git 에서 파일을 고치고 리뷰를 받습니다.**
- 대시보드 자체도 git 에 있습니다 — `scripts/build_pi_dashboard.py` 가
  차트·레이아웃·해석 규칙까지 전부 API 로 생성합니다. UI 에서 고친 차트는
  다음 실행 때 git 버전으로 되돌아갑니다. 의도된 동작입니다.
- 기획팀 계정은 **SQL 편집 권한이 없습니다.** 실수로 다른 정의를 만들 수 없습니다.

뷰는 짧게 씁니다. 짧아야 리뷰가 됩니다. 여섯 줄짜리 정의는 누구나 읽고
"이건 틀렸다" 고 말할 수 있지만, `->>` 가 여든 줄 들어간 쿼리는 아무도 못 합니다.

---

## 2. 세 가지 등급 (이름 규칙)

| 접두사 | 등급 | 뜻 | 예 |
|---|---|---|---|
| `v_kpi_` | KPI | 조직이 최종적으로 평가받는 결과 지표 | (현재 없음 — 3장 참고) |
| `v_pi_` | PI | 측정 가능하고, KPI 를 움직인다고 보는 선행 지표 | `v_pi_coaching_adherence_daily` |
| `v_bridge_` | Bridge | PI 와 KPI 사이의 연결과, **빠진 데이터**의 기록 | `v_bridge_pi_to_kpi` |

**접두사는 장식이 아닙니다.** 등급을 섞는 것이 이 구조가 막으려는 실패입니다.
선행지표(PI)를 결과지표(KPI)처럼 보고하면, "순응도가 올랐으니 재입원이 줄었다"
같은 검증되지 않은 주장이 슬그머니 사실이 됩니다.

---

## 3. 왜 KPI 뷰가 하나도 없는가

사업 문서의 핵심 KPI — 30일 재입원율, 재원일수(LOS), MSPB, 미수금 —
는 **전부 병원 재무·운영 지표**이고, 이 웨어하우스에는 입퇴원 기록도
청구 데이터도 없습니다. 계산할 방법이 없습니다.

NULL 을 반환하는 KPI 뷰를 만들지 않은 이유: 항상 0 이거나 빈 지표는
없는 것보다 나쁩니다. 언젠가 누군가 그 숫자를 인용하기 때문입니다.

대신 `v_bridge_pi_to_kpi` 에 **무엇이 없는지**를 데이터로 적어 두었습니다.
어떤 KPI 가, 어떤 PI 로 대체되고 있고, 계산하려면 어떤 데이터가 필요한지가
행으로 들어 있습니다. 데이터가 생기면 그때 `v_kpi_*` 뷰를 만들고
그 행의 상태를 바꿉니다. **이 등록부가 곧 할 일 목록입니다.**

## 4. 현재 있는 지표

| 뷰 | 무엇을 재는가 | 읽을 때 주의 |
|---|---|---|
| `v_pi_coaching_adherence_daily` | 일별 코칭 순응도 (%) | 분모는 전달된 **모든** 활동. 철회된 것도 포함 |
| `v_pi_coaching_adherence_by_domain` | 도메인별 순응도 | 식단/운동/수면/스트레스 비교용 |
| `v_pi_app_engagement_daily` | 일별 활성 사용자 수 | 액션 수가 아니라 **사람 수**. 한 명이 많이 눌러도 안 오름 |
| `v_pi_measurement_participation_weekly` | 주별 측정 참여자 수 | 주 단위. 기기 측정은 매일 하는 일이 아님 |
| `v_pi_population_risk_monthly` | 월별 평균 IRS+ | **백분위 순위**입니다. 추세만 의미 있음 |
| `v_pi_high_risk_disease_load_monthly` | 사용자당 고위험 질환 **개수** | 고위험 = 상위 20% (`irs_score >= 80`) |
| `v_pi_scoring_coverage_monthly` | 코호트 중 점수를 받은 비율 | **위험도 지표를 보기 전에 먼저 볼 것** |
| `v_bridge_pi_to_kpi` | 무엇을 못 재고 있는지 | 5장 참고 |

이 여덟 개가 그대로 **PI 지표 대시보드**(`/superset/dashboard/pi-metrics/`)의
차트입니다. 해석 규칙은 대시보드 맨 위 카드에도 붙어 있습니다.

### 반드시 알아야 할 해석 규칙

1. **IRS/IRS+/LRS/MRS/PRS 는 1~100 백분위 순위입니다.** 절대 위험도가 아니고,
   더하거나 뺄 수 없습니다. "IRS 에서 PRS 를 빼면 생활습관 기여분" 같은 계산은
   틀립니다 (IRS 는 머신러닝 결합 결과입니다).
2. **커버리지를 먼저 보세요.** 점수를 받은 사람이 줄어든 달에 평균 위험도가
   내려갔다면, 위험이 줄어든 게 아니라 아픈 사람이 측정을 안 한 것일 수 있습니다.
3. **질환은 35개만 사용자에게 보입니다.** 엔진은 44개를 계산하지만 9개는
   비공개입니다. 질환별 지표는 `is_in_catalog` 로 걸러야 합니다.

## 5. 새 지표 추가 절차

### 5-1. 먼저 물어볼 것

- 이건 **결과(KPI)** 인가, **선행(PI)** 인가? 접두사가 달라집니다.
- 이미 있는 지표의 다른 각도인가? 그렇다면 **뷰를 하나 더** 만듭니다.
  기존 뷰에 컬럼을 붙이지 않습니다 (한 뷰 = 한 지표).
- 지금 있는 데이터로 계산되는가? 아니면 `v_bridge_pi_to_kpi` 에 행을 추가할 일입니다.

### 5-2. 만들기

```bash
cd invites-loop-bi
# 1) 파일 생성: dbt/models/marts/metrics/v_pi_<이름>.sql
#    - 별(star) 스키마 위에 얇게 작성 (dim_*, fct_* 를 ref() 로 참조)
#    - 맨 위에 주석으로 "무엇을 재는지 + 해석 주의사항" 을 적습니다
# 2) 테스트 추가: dbt/models/marts/metrics/metrics.yml
#    - 최소한 키 컬럼에 not_null + unique
#    - 비율이면 accepted_range 0~100

source setup_env.sh
uv run dbt build --project-dir dbt --select metrics
```

### 5-3. 검토받기

git 브랜치 → PR. 리뷰 포인트는 하나입니다: **정의가 이름과 일치하는가.**

### 5-4. 반영

- 병합 후 다음 02:00 빌드에 자동 반영됩니다. 급하면 위 `dbt build` 를 수동 실행.
- **Superset 은 스키마를 자동 동기화하지 않습니다.** 새 뷰를 데이터셋으로
  등록해야 차트를 만들 수 있습니다:
  ```bash
  cd deploy/superset
  ./scripts/register_marts_datasets.sh
  ```
- PI 대시보드에 올릴 지표면 `scripts/build_pi_dashboard.py` 의 `CHARTS` /
  `LAYOUT` 에 추가하고 다시 실행합니다. 차트도 git 이 원본입니다.
- 권한은 따로 줄 필요가 없습니다. `marts` 에 새로 생기는 객체는
  `superset_reader` 가 자동으로 읽도록 설정되어 있습니다.

## 6. 자주 하는 실수

| 실수 | 왜 문제인가 |
|---|---|
| 대시보드 카드에 SQL 을 직접 쓴다 | 정의가 git 밖으로 새고, 리뷰가 사라집니다 |
| UI 에서 차트를 고치고 끝낸다 | 다음 `build_pi_dashboard.py` 실행 때 사라집니다. 스크립트를 고치세요 |
| 한 뷰에 지표를 여러 개 넣는다 | "이 뷰는 무슨 지표?" 에 답할 수 없게 됩니다 |
| PI 를 KPI 라고 보고한다 | 검증 안 된 인과관계가 사실처럼 굳습니다 |
| 테스트가 실패하니 임계값을 올린다 | 경보를 끄는 것이지 고치는 게 아닙니다 |
| 백분위 점수를 더하거나 뺀다 | 백분위는 산술 연산 대상이 아닙니다 |
| 질환 지표에서 `is_in_catalog` 를 빼먹는다 | 사용자에게 안 보이는 9개 질환이 섞입니다 |
